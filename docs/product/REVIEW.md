## R01 · P1 · 模拟复制不能按当前流程保证排除剪贴板历史

位置：`PLAN.md:228–236`；`RECORD.md:126–127`。

方案先往剪贴板写排除历史的格式，再给外部应用发送 Ctrl+C。但标记属于当前剪贴板内容，不能约束外部应用下一次复制；外部应用清空并写入新内容时，预先放入的标记可能一起被清掉。之后再补标记又存在历史监听先读取的竞争窗口。因此不能承诺“本次复制既不进 Win+V 历史也不同步到云剪贴板”。这是依据 API 行为作出的推断。[历史排除格式](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats)、[EmptyClipboard](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-emptyclipboard)

另外，`OleGetClipboard` 返回 `IDataObject`，可能继续向原应用发 RPC，不是自动完成的独立“全格式快照”。[OleGetClipboard](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-olegetclipboard)

建议：

- 保留默认关闭，但将承诺改为尽力恢复，明确历史、云同步和第三方监听无法保证排除。
- 定义可安全快照的格式与大小上限；不能恢复时，应在模拟复制前拒绝借用或采用明确降级。
- 记录剪贴板序列号、来源窗口和本次操作状态；用户期间又复制了内容时，不能把旧快照强行写回。
- 区分自身写入、目标应用复制与无关剪贴板更新，避免把自身事件当成 Ctrl+C 的结果。

验收应包含富文本、图片、文件列表、延迟渲染，以及用户在 300 ms 等待窗口内再次复制的情况。

## R02 · P1 · 二进制句柄契约不足以实现全部内置服务

位置：`PLAN.md:383–386`、`PLAN.md:479`。

当前只定义原始 body/multipart 中的文件句柄，以及将整个响应保存为文件。实际首版包含 JSON 内嵌二进制的服务：Google TTS 返回 `audioContent` Base64 字段，腾讯基础 TTS 返回 `Audio` Base64 字段。把响应原样存文件得到的是 JSON，不能作为音频播放；让插件解析完整音频字符串又违反“字节永不进插件”。[Google TTS](https://docs.cloud.google.com/text-to-speech/docs/create-audio)、[腾讯 TTS](https://cloud.tencent.cn/document/product/1073/37995)

腾讯 OCR 本地截图走 `ImageBase64` 也需要宿主侧的 JSON 字段编码能力；仅声明“body 引用句柄”尚未规定如何生成该字段。[腾讯 OCR 接口说明](https://cloud.tencent.com/document/product/866/116115)

建议在冻结 `$http` 前加入：

- 请求：指定 JSON 字段由文件句柄生成 Base64，明确序列化、长度限制，以及在最终请求体生成后计算签名。
- 响应：指定 JSON 字段提取并 Base64 解码为文件句柄，同时把其余元数据返回插件。
- 句柄：归属的插件、任务、使用期限、引用计数、最大大小，以及任务取消后的释放规则。
- 错误：HTTP 状态、响应头、供应商错误体应可判定；目前 `$http` 尚未明确返回封装，插件难以可靠区分 401、429、5xx 和读取 Retry-After。

用一条截图请求、一条 multipart ASR 请求、一条 JSON/Base64 TTS 响应、一条原始音频响应验证同一套契约。应把这些验证提前到 M1 的契约验收，避免 M3 才破坏 API v1。

## R03 · P1 · 默认视频翻译批次超限，且没有字幕逐条对齐协议

位置：`PLAN.md:355–363`、`PLAN.md:637–638`。

视频默认取第一个启用的翻译引擎，初始配置即 MyMemory；但批次拟为约 1500 字符或 20 条。MyMemory 的 `q` 上限是 **500 个 UTF-8 字节**，不是 500 字符，约 167 个常见汉字就会超限。主窗口及 OCR 长文本也受影响。[MyMemory 官方规格](https://mymemory.translated.net/doc/spec.php)

另一个独立问题：`TranslateResult` 只有一个 `text`。即使选用支持长文本的服务，把 20 条字幕拼成字符串翻译，也不能保证返回恰好 20 行；合并、拆行或模型增加说明都会使原文、译文与时间码错位。

建议：

- 能力声明补充按字节/字符/token 计算的上限、批量条数上限、是否保留条目身份等信息；可由插件封装供应商限制，但宿主与插件之间必须约定责任。
- 视频请求按 `segmentId` 传入，按 ID 返回结果；单文本引擎由适配层逐条处理，不能以换行符作为对齐协议。
- 规定单条仍超限时的切分与合并规则；合批结果缺项、多项、乱序时验证并降级。
- MyMemory 的每日额度只适合作为短文本默认路径，长任务启动前应显示所选引擎及估算用量，避免识别完成后翻译大量失败。

验收必须包括默认 MyMemory、中英混排长句、结果条数不匹配、字幕内自带换行。

## R04 · P1 · ASR 只有平台名，尚未确定字幕能力与编码协商

位置：`PLAN.md:363`、`PLAN.md:473–479`、`PLAN.md:629–636`；`design/SetSpeech.dc.html:84`。

复用 AI 平台的 key 不等于复用翻译模型，也不等于各模型都能稳定返回 `{start,end,text}`。例如 OpenAI 文档明确 `timestamp_granularities[]` 只适用于 `whisper-1`；其他模型需分别核对其输出协议。Gemini 文档展示通过提示与结构化输出生成时间标记，也不能直接据此假定得到经过精确对齐的起止时间。[OpenAI 转写文档](https://developers.openai.com/api/docs/guides/speech-to-text)、[Gemini 音频文档](https://ai.google.dev/gemini-api/docs/audio)

此外，示例声明 `container: wav`，下一句却规定“声明体积上限的走 AAC 编码器”；体积上限并不能证明服务接受 AAC 或其容器。VAD 同时承诺“不切断句子”和“每片 ≤5 分钟”，在长时间无静音时也没有可执行的回落规则。

建议：

- 分离“凭据账户”“翻译模型”“转写模型”；明确首版经过验证的模型和输出格式。
- 区分纯文本转写与带时间码转写能力；视频入口要求后者，普通语音翻译可接受前者。
- 声明可接受的容器、编码、采样率与声道组合，由宿主选择交集，再同时满足体积和时长约束。
- 时间码检查范围、单调性、重叠和空段；明确字幕误差验收指标。
- 无静音点时允许硬切、少量重叠与去重，并保留媒体时间轴，不能通过删除静音导致字幕整体提前。

应在 M1 冻结 ASR 契约前做短样本验证，完整媒体管线仍留在 M3/M4。

## R05 · P1 · 密钥保护和宿主代理缺少完整的信任边界

位置：`PLAN.md:295–297`、`PLAN.md:391`、`PLAN.md:462`、`PLAN.md:560`。

“插件不直接读取密钥”是有价值的目标，但不等于“密钥永远不会进入插件”。当前插件可描述 URL、请求体和占位符，宿主又把服务端响应交回插件；获准的远端若回显请求内容，密钥仍可能随响应回来。AppContainer 不能防止宿主主动代理这类操作。

还存在一个容易实现错的具体场景：用户选中的原文本身含 `{{secret.apiKey}}`。若对最终 JSON 的所有字符串做替换，这段普通待翻译文字就会被替换成真实凭据并上传。密钥引用必须与用户文本有结构上的区别，不能靠对最终请求做全局字符串替换。

建议在威胁模型和协议中明确：

- 凭据绑定插件/账户及获准目标 origin；共享腾讯、OpenAI 等凭据只能经用户认可的绑定关系，不能靠第三方声明同名 secret 获得。
- 使用显式、不可与普通文本混淆的 secret 引用；只在被允许的位置解析，规定 URL 编码及签名顺序。
- 重定向逐跳校验目标，禁止把认证头带到未授权 origin；动态地址按 scheme/host/port 控制。Ollama、AnkiConnect 的本地 HTTP 是明确例外，不能据此全局放开内网和明文凭据。
- `audioUrl`、更新 URL、代理测试、WebSocket 等宿主网络入口也走统一策略，不能只检查 `$http`。
- IPC 绑定任务与调用者；文件句柄、KV、签名请求均验证归属，限制消息长度、并发、响应体及日志大小。
- 日志与异常不记录密钥或完整敏感请求；不能因密钥不进入 `ctx.config` 就认为 `detail`、URL 和响应日志安全。

“明文从不进入任何 WebView”还与现有 HTML 设置页输入 API Key 相冲突。要么将凭据输入/导入密码改为宿主原生控件；要么明确允许可信设置页在用户输入期间短暂持有，保存后清空、已有值只显示占位状态。两种都可行，必须选一种，不能同时承诺。

UI 还会展示不可信译文、词典数据及第三方 SVG。应规定文本渲染/净化、CSP、导航限制与按窗口授权的消息白名单，避免界面注入取得宿主能力。[WebView2 官方安全建议](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)

## R06 · P1 · AppContainer 的安全承诺超过当前配置描述

位置：`PLAN.md:126–139`、`PLAN.md:724`。

不授予网络能力可以限制直接联网，但 **AppContainer 并不天然意味着不存在任何可写文件系统**。官方描述包含应用自己的可写虚拟注册表及应用数据目录。只验证用户文档和插件目录不能写，不能证明文档中的绝对承诺。[AppContainer for legacy apps](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-for-legacy-applications-)

建议把保证限定为“不允许写用户数据和程序目录，仅允许明确列出的容器资源”，或者明确补上实现完全禁写所需的配置与验证。M0 还需验证：容器 profile 创建/删除、EXE/DLL/插件目录 ACL、命名管道双端访问控制、拒绝非目标进程连接、句柄继承、Job Object 限额和父进程异常退出。

同一子进程内多个 `JSRuntime` 提供 JS 层隔离，不是引擎原生漏洞发生后的插件间隔离。引擎被攻破后可能触及其他运行时及共享 IPC，不能继续依赖子进程自报的 pluginId 实现原生攻击后的强隔离。这与“不做每插件独立进程”的取舍可以兼容，但威胁模型必须写清。

验收除了直接 socket/file 操作，还要用恶意插件请求宿主代为越权，覆盖宿主代理这条实际开放的出口。

## R07 · P2 · 任务、流式输出与取消还没有统一状态机

位置：`PLAN.md:303`、`PLAN.md:325–327`、`PLAN.md:507`、`PLAN.md:584–586`、`PLAN.md:642`。

典型触发场景：用户连续翻译 A/B，A 的流式块晚到；一个窗口折叠 OpenAI 卡片，但另一个窗口仍在用同一插件；视频暂停后服务被禁用；网络断开前已经输出半段译文。这些操作目前没有共同的状态和归属规则。

建议最少定义 `jobId/requestId/generation/providerInstanceId`、任务状态转移和终态。旧 generation 的结果丢弃；取消按调用处理，销毁整个运行时仅用于强制恢复，并结算该运行时所有未完成调用。流式重试需定义清空重来或替换结果，不能直接追加导致译文重复。

还应确定：

- 单插件多调用如何调度；死循环时多久中断，是否会阻塞其他运行时。
- 全局/账户/服务并发限制、流式消息背压、总内存上限及崩溃重启退避。
- 超时、网络、429 的重试预算及 Retry-After 上限；`vocab` 写操作必须有幂等/去重，不能通用重试制造重复单词。
- 关闭、最小化、保温、释放 WebView 对后台转写任务的不同影响。
- `dictionary` 与 `translate` 同时存在时，同一服务卡片请求哪一个、是否复用结果；当前“并行词典查询”不能绕过折叠卡片不请求的原则。

这些规则应在 M1 落成状态表和少量竞争条件测试，而不是交给各窗口自行实现。

## R08 · P2 · 性能目标有意义，但预算模型与验收场景不足

位置：`PLAN.md:29`、`PLAN.md:183–204`、`PLAN.md:326`、`PLAN.md:703–716`。

目前没有实测，不能确认 25 MB/60 MB 和包体目标能达到，也不能据此宣布不可行。能够确认的问题是预算没有充分覆盖多窗口保温：文档按每个窗口一个 WebView 并保留所有已开窗口，但表内只列一份 8–15 MB 渲染进程成本。实际进程共享应测量，不能按一次单窗口结果外推。

另有三处验收口径需要收敛：

- 冷态窗口可见 ≤150 ms 与 WebView 首帧 ≤300 ms 的区别是什么？若前者允许先显示空 Win32 壳，就另测“内容可见/可交互”，避免空白窗口通过验收。
- 全部窗口关闭后 10 分钟释放，读数又要求静置 5 分钟，测试要记录明确的时间线和状态，避免把冷态当保温态。
- 每插件 64 MB（最高 256 MB）与整个宿主闲置 5–10 MB 并非逻辑上直接矛盾，但长期保留数据、KV 缓存或运行时泄漏会使其失守；需限定默认插件集合及“处理大输入后再闲置”的场景。

建议 M0 固定 Windows build、WebView2/SDK/.NET/引擎版本、CPU/RAM、x64 或 ARM64、DPI；同时记录 private working set、private bytes/commit，以及 P50/P95。至少测首次冷建、一次热开、开过所有窗口后的保温、长音视频任务结束后闲置、全部内置插件启用。

体积预算另列 SQLite 原生依赖、WebView2 loader、签名库、安装器资源与用户数据目录增长。WebView2 系统安装不计入应用包体合理，但用户数据缓存不能从磁盘使用说明中消失。

## R09 · P2 · UIA 回落需要线程、超时及焦点策略

位置：`PLAN.md:214–243`。

“首次查询超过 300 ms 就跳第三级”没有说明如何在同步 COM 调用尚未返回时停止等待。仅加 stopwatch 无法限制一个卡住的 provider；若在消息泵上做 UIA，会同时影响托盘和快捷键响应。微软建议 UIA 在不拥有窗口的独立 MTA 线程上调用。[UIA 线程模型](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading)

应补充独立线程/超时能力、晚到结果丢弃、阻塞调用的回收策略，以及重复失败目标的退避。还要先记录前台窗口和焦点，再显示会抢焦点的界面；判定无选区、空选区、多选区、密码字段与用户在取词期间切换程序。

M0 的“10 个程序”应覆盖具体控件：浏览器页面正文/PDF、编辑器、终端、Office、普通 edit、提升权限窗口及无响应程序。不能由框架名称直接推导所有控件都支持选区读取。

这部分需要验证，但不需要因此推翻 UIA 优先、可选复制回落的总体方向。

## R10 · P2 · 原型复用和自动生成设置页之间缺少实现层

位置：`PLAN.md:132`、`PLAN.md:305`、`PLAN.md:460`；`design/README.md:23–33`；`design/SetAI.dc.html:84`；`design/SetVocab.dc.html:84`。

`design/README.md` 已明确原型依赖仓库没有的 `support.js`、`DCLogic` 和模板替换。原型还包含硬编码文案/颜色以及用 span/div 表现的输入控件。因此能复用视觉结构，但当前资源不能直接当生产 WebView 页面交付。M1 应显式包含独立前端构建、组件、token、资源表及宿主桥接工作。

自动设置页也并非只有静态 JSON Schema：Ollama 画板有“拉取列表”，Anki 有目标牌组，TTS 有音色；契约只定义 `voices()`，尚无模型和牌组的受限动态选项接口。腾讯跨插件共享凭据、OpenAI 翻译/ASR 共用账户、多个能力分别启停，也缺账户与服务实例的数据模型。

建议先定义三层身份：插件包 → 凭据账户/配置实例 → 能力服务。动态选项采用有限、类型化的宿主调用接口，避免为每个内置服务另写特殊 UI。还应定义：

- 多能力插件的某个服务禁用时，是否仍保留其他能力及运行时。
- 翻译引擎页与 AI 页各自拖拽，如何表达同一个跨页全局卡片顺序。
- 提示语、等级、流式开关、temperature、用户超时覆盖 manifest 超时的优先级与不支持时的处理。
- 不符合 JSON Schema 的手改配置如何回退并保留可恢复副本。

## R11 · P2 · 数据保留、收藏同步及导入缺少故障语义

位置：`PLAN.md:530`、`PLAN.md:550–562`、`PLAN.md:612`、`PLAN.md:643`、`PLAN.md:654–659`。

`cache/` 写的是截图与音频“退出时清理”，OCR 又写截图默认保留 7 天，原型写“存到图片目录”。可能本意是临时截图和用户保留副本两份，但方案尚未说明这两个对象。

建议分清临时资源、用户保留截图、生词数据、WebView 用户数据和日志，逐项定义位置/最大容量/保留期/清理触发。异常退出时不会执行正常清理，因此还需下次启动回收过期临时文件；正在转写的句柄不能被清理器删除。运行缓存适合放 LocalAppData，避免与漫游配置混为一类。

收藏队列需按目标分别记录同步状态，例如 Anki 成功、欧路失败、CSV 已导出不能只共用一个“已完成”。补齐词条去重键、重试、远端 ID、取消收藏、重复导出策略；如果用户要管理 128 条待导出内容，需要队列查看/删除入口，或明确首版不提供管理。

设置、凭据和数据库迁移还需原子写入、备份/回滚、并发编辑冲突策略；导入要先完整校验再统一提交，定义替换还是合并，以及导入包是否含词库和插件。加密格式应带版本、KDF 参数上限和认证失败处理，避免损坏或恶意包引发不可控开销。

## R12 · P2 · 插件安装和更新还不能保证权限延续及可恢复

位置：`PLAN.md:491–498`、`PLAN.md:691–698`。

安装时确认 hosts，而插件更新只描述校验哈希再覆盖。如果新版本增加 hosts 或修改动态地址来源，没有规定重新确认，原授权边界就会被更新隐式扩大。第三方清单与包同源时，哈希只能验证文件一致性，不能证明作者身份；已有签名包的后续版本也不能静默退化为未签名。

建议补充：权限差异确认、签名身份连续性、版本回退政策、原子暂存/切换、失败回滚、正在执行任务的处理。ZIP 校验应明确禁止路径穿越、绝对路径、符号链接逃逸、大小写重复路径，并限制文件数、解压后大小及压缩比。

应用更新需定义签名覆盖的确切字节、密钥轮换、下载取消/重试、安装失败后的状态、数据库迁移与二进制回滚的兼容性。不要把“签名不通过”在用户主动检查更新时表现成“已经是最新版”。

## R13 · P2 · 窗口、DPI 与离线规则有可见的产品缺口

位置：`PLAN.md:104–110`；`DESIGN.md:269`、`DESIGN.md:298–324`。

- 设置窗口固定 900×700。在 1920×1080、150% 缩放下，逻辑工作区高度小于 720，扣除任务栏后可能放不下 700 高窗口；更小屏幕更明显。标题栏中点可见不能保证底部按钮可达。明确尺寸单位，按工作区限制最大尺寸，内容滚动。
- 悬浮窗“高度由内容撑开”需增加最大高度与内部滚动，否则长 OCR/语音文本会把关闭或操作区推出屏幕。
- 明确 Per-Monitor DPI、跨屏拖动、负坐标、显示器断开及截图物理像素到结果坐标的换算；`WM_NCCALCSIZE` 本身不能解决 WebView 中 CSS 像素和物理像素的对应。
- “其余窗口尺寸固定”与主窗口/结果窗最大化按钮并存，需明确是否允许最大化、调整大小及 Snap 行为。
- 网络整体不可达时“全部卡片折叠”会误伤本机 Ollama；本机 TTS、AnkiConnect 也不应因公网断开停用。离线应按具体请求路径/服务区分，不能用单一全局布尔值停用全部能力。
- 补 Tab/Shift+Tab、焦点可见、Enter/IME 组合输入、Esc 作用域及列表键盘操作。可访问性不能只停留在图标 aria-label。

## 建议的推进顺序

1. **先修正 R01–R06 的方案承诺和协议缺口**，尤其是句柄变换、字幕条目 ID、ASR 模型能力及凭据输入边界。
2. **M0 做真实 Windows 可执行闭环**：NativeAOT → WebView 首帧；AppContainer → IPC → 宿主网络；UIA 取词及受控超时；多窗口保温和释放。明确支持的 CPU 架构、Windows build 及依赖版本。QuickJS-NG 先作为基线，只有数据说明需要时再投入完整退路实现。
3. **M1 用代表性服务证明契约完整**：无鉴权 GET、TC3 签名、SSE、multipart 音频、JSON/Base64 图片和音频、逐条字幕翻译。后几项可以是小型契约探针，不必提前实现完整 OCR/录音 UI。
4. **M2–M4 再铺开功能与服务数量**，M5 完成安装、更新、导入回滚及真实服务冒烟测试。录制响应的契约测试有用，但不能代替真实服务对鉴权、限制及返回结构的验证。

经官方文档核对，Media Foundation Source Reader 在 Windows 8 起支持音频重采样，因此当前 Windows 11 范围下“系统解码并重采样”的方向不需要推翻；需要验证的是具体容器/编码组合与失败出口。[SetCurrentMediaType 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/mfreadwrite/nf-mfreadwrite-imfsourcereader-setcurrentmediatype)

工程工作量的主要不确定性来自自建插件平台及多套原生互操作，而非卡片页面。由于尚无实现基线、团队规模和投入时间，当前不能给出可信的工期承诺；应在 M0 后按实测与完成的互操作范围估算。
