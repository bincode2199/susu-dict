## 第 1 轮：宿主与项目适配

审查输入：沙箱内/外只读系统查询、apt 本地索引、GitHub 匿名 REST 元数据、ARCHITECTURE/DEV-PLAN/TEST-PLAN、Microsoft/QEMU 官方依据。

| 问题 | 处理 | 结果 |
|---|---|---|
| 沙箱缺 `/dev/kvm` 可能被误判成无法虚拟化 | 沙箱外确认设备存在、模块加载；进一步打开设备确实被权限拒绝 | 区分硬件能力与用户权限；P1 解决权限后验证 |
| 把 64 GB 总内存当可分配空间 | 按 available 约 34 GiB，分配 16+8，并设 8 GiB 宿主余量 | 两台按需运行，资源不足顺序执行 |
| 普通镜像方案容易只约束 qcow2 路径 | 固件、VARS、TPM、socket、临时文件、备份均进入每台目录；直接 QEMU 管理 | 第 4 节列出路径验收 |
| GitHub 默认分支不能假定 main | 公开 API 确认 master/public | 工作流触发对齐 master |
| 项目不存在可执行源码，不能写现成 CI 承诺 | F00 落成入口后接 CI；说明所有工作流仍待实现 | 与 DEV-PLAN 状态一致 |
| 单一开发机无法证明用户安装无 SDK 依赖 | 增设独立 clean，不安装 SDK/Node/runner | 符合 NativeAOT 与 F18 验收要求 |

本轮结论：宿主资源和项目技术路线匹配；软件安装、KVM 权限、介质/许可属于明确实施输入。没有实测 Windows 启动成功。

## 第 2 轮：反例、安全与交付链

逐项推演：外部 PR、宿主内网暴露、锁屏/Session 0、RDP 音频、签名后字节变化、人工测试跨工作流、回滚后 TPM 不一致、备份中途磁盘耗尽。

| 反例 | 修订或核对结果 | 关闭条件 |
|---|---|---|
| 外部 PR 利用持久 self-hosted runner 访问开发环境 | 首期只用 GitHub 托管 runner；本地只接维护者确认的候选 | 无公开 PR 到本地 runner 路径 |
| NAT 被误当作隔离 LAN 的防火墙 | 明确 NAT 不提供这种隔离；未来自动 runner 要独立隔离及 IPv4/IPv6 探测 | 第二阶段隔离验收前不启用 |
| Windows service 里跑 UI 测试，或 RDP 断线改变会话 | 使用解锁控制台；RDP 作为单独场景 | 桌面/焦点/音频实测留待安装阶段 |
| 修改 HOME 影响个人工具与凭据路径 | 改为各组件显式状态/缓存路径，不改写 HOME | 文件句柄与 canonical path 检查 |
| 候选通过后签名改包，旧证据被拿来发布 | 最终签名包重新验收；证据绑定最终 hash | promote 校验 SHA/run/artifact/hash/必需测试状态 |
| 人工 clean 验收使一个 workflow 长期等待 | 明确 release prepare/promote 两次手动执行 | 两次执行之间通过不可变产物与维护者证据衔接 |
| 只回滚 qcow2，TPM/BitLocker/UEFI 状态错位 | 冷备份整个状态集合；保留恢复密钥 | P7 实际整套恢复演练 |
| 替换备份需要同时保留新旧两份，700 GiB 稳态预算不足 | 补充最多 1,000 GiB 短时预算 + 200 GiB 宿主余量，逐台备份回退 | 不先删唯一可恢复基线 |

本轮结论：上述设计缺口已在计划中修订；没有用“runner 标签”“NAT”“文件存在”替代真实隔离或验收。

## V2 第 1 轮：按新要求修订

用户要求：缩小磁盘；不做完整备份，代码使用 Git；虚拟机当前服务 susu-dict，但未来供其它项目复用。

- 将名称改为 `win11-dev` / `win11-clean`；各自目录仍位于 `/data/vm`，没有执行目录迁移。
- 磁盘改为 120 + 80 = 200 GiB；介质/临时产物等 40 GiB、关键导出 10 GiB，工作预算 250 GiB，另留宿主 50 GiB，即初期准备约 300 GiB 空间。
- 删除整机备份、黄金镜像和持续快照的实施要求；P4/P7 改为记录配置、重装及关键数据恢复演练。初版 700/1,000 GiB 预算失效。
- 代码只按日常 Git 流程提交并 push，不额外安排本地定时备份；关键非代码数据按需导出。
- 区分通用环境和 susu-dict 配置；工作区、工具版本、凭据、报告按项目管理。其它项目不继承 susu-dict 的 master/.NET/NSIS 假设。

## V5 第 1 轮：故障路径复审

本轮从首次安装、正常启停、失败处理与重建的顺序推演 V4。只读复核真实宿主机 `/data` 为 ext4 读写挂载，约空闲 1.5 TiB；系统盘约空闲 318 GiB。沙箱内显示的只读挂载已经在宿主机复核排除，未误判为系统故障。

| 优先级 | 发现 | 修订 |
|---|---|---|
| P1 | 只检查目录存在和容量，不能防 `/data` 未挂载时写入根分区 | §4.1 检查实际文件系统、UUID、可写状态，不一致即拒绝写操作 |

| P2 | 进程存在无法判断磁盘错误暂停，关机/重启语义可能被参数改变 | §4.1 固定 I/O 错误策略，查询 QMP 状态，禁止自动重试与不适合的退出参数 |

## 实施后第 1 轮：逐项验收与反例

2026-09-21 对照 V5 第 8 节、两台运行控制器与各自 `evidence/` 复核。开发机 8 vCPU/16 GiB/120 GiB、clean 4 vCPU/8 GiB/80 GiB，配置和状态分别独占 `/data/vm/win11-dev` 与 `/data/vm/win11-clean`。QMP 在实际启动中报告 KVM enabled；Windows 内显示 Pro 25H2 build 26200.9457、Secure Boot=True、TPM Ready=True、VirtIO 系统盘 Healthy、设备错误为空。两台 DNS、Windows Update、防火墙、UAC、Defender、Guest Agent、WinRE、RDP 关闭及初始账户分组均有直接证据；许可状态明确为 Notification，按用户安排待激活。

反例检查发现 clean 在锁屏状态下，SYSTEM 会话音频播放和录音虽然能打开端点与 SPICE 通道，采样仍近乎静音。先前仅凭“设备状态 OK/通道打开”不能判定音频通过。使用机主给定的标准账户登录后，各机通过合成音频的双向非零采样实测，未把无物理扬声器/麦克风的情况说成人工听音。临时热插拔 USB Audio 对照设备已移除，HDA 恢复后再查设备错误列表仍为空。

clean 的重建在导出样例并由 guest、交换盘清单和宿主三方校验后才重置系统盘/VARS/TPM；重新安装、更新、账户降权、VirtIO 切换与恢复后，SHA-256 一致。独立小镜像注入 EIO 后，QMP 显示暂停在 `io-error` 且 `io-status=failed`；实际两台系统盘未用于故障注入。两块 qcow2 离线检查均无结构错误。结论：主要功能、数据恢复与故障暂停有直接证据，没有以安装进度或文档推断替代运行验收。
