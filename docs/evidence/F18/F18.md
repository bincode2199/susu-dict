## F18.1 · NSIS per-user installer (2026-10-02)

### Bug found and fixed

`VocabService.StopAsync` awaited its loop on the UI synchronization context, and `Program` calls it with `GetResult()` after the message loop ended. After any exit request the process stayed alive (`app.exit` never logged, mutex held). Found by the real-instance installer test; fixed with `ConfigureAwait(false)`. This also affected the tray Exit whenever the vocabulary loop was running.

## F18.2 · Application update pipeline (2026-10-02)

Conclusion: the signed-manifest verifier, Ed25519 keyring and rotation, anti-rollback state, the journaled staged updater with a paired backup of the old binaries and database, health check, rollback and recovery, the check-only schedule, and the Settings About/Update page are built and tested. **Nothing was invented that a release must supply:** the production key slot is empty (an unsigned build says so and verifies nothing), and no update endpoint is registered. Install runs only when the user clicks it.

| Piece | Where | Behaviour |
|---|---|---|
| Manifest and signature | `src/Susu.Plugins/AppUpdate/UpdateVerifier.cs`, `UpdateTrust.cs` | Detached signature file (three fixed lines: key id, `ed25519`, base64) over `susu-update-v1` plus newline plus the raw manifest bytes. Order: size limits, rotation records, signature, only then YAML parse (strict schema: unknown or duplicate keys and aliases rejected; the package file name is a bare `*.zip` name beside the manifest, never a URL). The signature file must be byte-exact canonical. Reuses `Ed25519` from F16.1. |
| Keyring and rotation | `UpdateKeyring`, `KeyRotation` | `UpdateKeyring.Production` is the production slot: **empty, marker `production-slot-empty`**. Test keys live only in the test assembly. A rotation record (add/revoke, numbered 1..n in order, domain `susu-keyring-v1`) must be signed by a key the current chain trusts for rotation and can never empty the release or rotation keys. Accepted records are stored as raw bytes and re-verified from the embedded roots at every load, so editing `trust.json` cannot add a key. A rotation is remembered only after the manifest itself verified. |
| Anti-rollback | `UpdateTrustStore` | The highest verified sequence and version are kept; an older sequence, an older version, or a version below the installed one is `rollback`. |
| Source | `UpdateSource.cs` | `IAppUpdateSource` port; `SignedManifestAppUpdateSource` over an `IUpdateTransport` (https only, size-limited, redirects to non-https refused). The URL is read from `updates/update-source.json` (`manifestUrl`); **none is registered by default**, no endpoint is invented. A transport failure is `network`, a verification failure keeps its own code; neither is ever "up to date" or a version. |
| Schedule | `UpdateSchedule`, `UpdatePrefs` | 15 s after start, then one check when 24 h have passed since the last attempt (a failed attempt counts; persisted in `updates/schedule.json`); serial; one sleep to the next due time, no polling; automatic checks can be switched off. It runs the application check and the plugin check (F16.2) from one schedule and never downloads or installs the application. |
| Staged journal | `AppUpdater`, `updates/journal.json` | Stages: Downloading, Staged, Exiting, BackedUp, Replacing, Replaced, Migrating, Migrated, HealthChecking, Healthy, Committed, RollingBack, RolledBack. Each change is an atomic replace. The package is checked for exact size and SHA-256 against the verified manifest, unpacked with bounds (entry count, size, path rules: no traversal, drive, stream, reserved names, case-duplicates, links, temp-suffix names) and every file hashed. |
| Paired backup and rollback | same | After the app exited: the old install folder (with a hash index) and the database (SQLite backup API, includes WAL pages) are copied to `updates/backup`. Replacement is per file (flushed temp, `File.Replace`). Any failure from the first replaced file on, and every interrupted stage from Replacing to Healthy, restores both together and verifies them against the index; a damaged backup is reported `rollback-incomplete` and retried at the next start. Before the first file is replaced a failure only returns to "staged". Commit is the Committed marker; the backup pair stays until the next update (for the F18.3 fallback). |
| Exit coordination | `src/Susu.Host/UpdateHost.cs` | Same message-window protocol as F18.1 (`InstallerSupport.RequestExit`); nothing is killed; a timeout aborts before anything changes. |
| Helper | `susu.exe --apply-update` and `--recover-update` | Install starts a copy of the exe (plus `e_sqlite3.dll`) under `updates/helper/<id>` that takes a named update lock, runs the updater, then starts whichever version is on disk. The page sends no path or URL; the install folder is the app's own. At start the app finishes harmless stages itself and starts the helper in recovery mode when the install folder may be half replaced. Probes run from the new exe: `--update-migrate` (database open with the build's own migrations) and `--update-health --expect-version`. |
| Settings page | `ui/src/components/UpdateSettings.vue`, `src/Susu.Ui/AppUpdate.cs` | Section in About: version, unsigned-build marker, no-source message, check, download, install with a second click that names the interrupted tasks, discard, automatic-check switch, last check, error keys in zh and en. Commands `Update.Check/Download/Install/Discard/AutoCheck` are Settings-only; contracts are generated (`ContractsGen --check` clean). |

### Kill points covered (fault at each step, a fresh updater recovers)

`download:begin`, `stage:begin`, `stage:hashed`, `stage:extracted`, `stage:journal`, `exit:journal`, `exit:requested`, `exit:done`, `backup:begin`, `backup:app:0..3`, `backup:db`, `backup:index`, `backup:journal`, `replace:journal`, `replace:0..3`, `replace:deleted`, `replace:done`, `migrate:begin`, `migrate:done`, `health:begin`, `health:done`, `health:journal`, `commit:journal`, `commit:cleanup`, and during a rollback `rollback:journal`, `rollback:file:n`, `rollback:files`, `rollback:db`, `rollback:done`. After each: the install folder and database are a matching pair (all old, or all new and committed), no temp leftovers, recovery is idempotent, and the update can be run again. Disk full is injected at the backup, replace and migration steps and while unpacking.

### Not executed and open

- **No production signing key and no update endpoint**: a release must embed the offline root public key (and the release keys) in `UpdateKeyring.Production` and provide the manifest URL. The URL is read from `updates/update-source.json`; it is not in the settings schema yet, and the HTTP client does not use the app's proxy policy (Susu.Net) yet.
- A real update of a running installed app (exit protocol plus helper restart) and a real power cut were not run; the real exe was exercised against a temp install folder with no instance running, and crashes were simulated at named steps.
- The manifest schema (fields, the `sequence` counter, `keyring-N.yaml` rotation files next to the manifest, the signature file format) is this module's design; PLAN specifies only "signed YAML, signature verified first".
- Anti-rollback high-water marks are not signed; F18.3 documents the threat model and keeps them unsigned (see Decisions under F18.3). Rotation records carry no effective-version rule; a revoked key stops working at once.
- (Resolved in F18.3) Replacement used to remove every file not in the package; it now removes only files an earlier version is known to have brought.

## F18.3 · Interruption, first-start failure, fallback, tampered input, uninstall (2026-10-02)

Conclusion: a tampered helper command line, an arbitrary EXE or folder, link tricks and a package swapped after verification cannot make the helper run or replace anything that is not the verified stage of this install folder. A new version that fails its first starts is rolled back (binaries and database as a pair) and not offered again; the user can also go back to the previous version while the backup pair exists. Uninstall keeps data by default, deletes only folders named `Su-Su`, and unlinks links inside them. Tested with the real published `susu.exe` and temp folders (`susu-f18-*`). **Not run:** a real update of a running installed app, a real power cut, and the app-level first-start gate through a real GUI start (see Open).

| Piece | Where | Behaviour |
|---|---|---|
| Path rules | `src/Susu.Plugins/AppUpdate/UpdatePathRules.cs` | An accepted path is an absolute `X:\...` of plain names. Refused: relative and drive-relative forms, `.` and `..`, empty segments, UNC, `\\?\` and `\\.\`, any `:` after the drive (alternate data streams), reserved device names, trailing dot or space, control characters and shell metacharacters, over 240 characters, network drives. A folder must not be a reparse point. The install folder must hold a regular `susu.exe`, not be a drive root or under the Windows folder, and not overlap the updates folder. |
| Helper command line | `UpdateHost.TryParse` and `Run` | Each option once, one value that is not an option; an unknown option or a missing value exits 2. `--rollback-update` needs `--reason` of `user-rollback` or `first-start-failed`; no other command takes a reason; `--expect-version` is digits and dots. `--report` must be a plain `.json` path outside the install folder. The helper must run from `updates\helper\...` of its own data root (the copy the app made), so a copy of the exe from anywhere else is refused. Probes (`--update-migrate`, `--update-health`) take no install folder. |
| Install-folder binding | `UpdateJournal.InstallDir`, `BackupIndex.InstallDir` | The journal and the backup index record the install folder they were made for; a helper told to work on another folder refuses (`install-dir-mismatch`; rollback `no-backup`). Journal and backup paths are re-validated as plain relative names on read; a journal or index naming a path outside the install folder is treated as damaged. |
| Package verification | `AppUpdater.Stage` | The package must be a plain file inside the updater's own downloads folder (`download-path-invalid` otherwise); the updates, downloads, stage and backup folders must not be junctions or symlinks. One handle (writers and deletes denied) serves the size check, the SHA-256 and the unpacking, so the verified bytes are the unpacked bytes. |
| Verified bytes only | `Apply`, `Replace` | The whole stage is re-hashed before the app is asked to exit; each staged file is hashed again while it is copied into the install folder (a swap in between is `stage-corrupt` and rolls back); the installed files are compared to the package again before the new exe is run for migration. No target or folder between it and the install folder may be a reparse point (`replace-failed`). |
| Replacement set | `Replace`, `installed-files.json` | Only files from the package are written. Files of the previous version that the new one no longer ships are removed only when they are in the list the updater wrote at its last commit or in the installer's `staged-manifest.json` (read before the first replacement). Other files in the install folder are the user's and stay (the backup still holds them; rollback restores changed ones and leaves unknown ones). |
| First-start guard | `FirstStartGuard`, `Program.FirstStartGate` | The commit arms `updates/first-start.json` (version, attempts 0). Each start of that version counts an attempt before anything else runs; 15 s after the message loop is up the app confirms and the guard is released. The third unconfirmed start does not run: the app starts the helper with `--rollback-update --reason first-start-failed` and exits. A damaged state file counts as "attempts used up", so a corrupt file never hides a crash loop; if no helper can be started the guard is cleared and the app runs. |
| Fallback | `AppUpdater.RollBackToPrevious`, helper `--rollback-update` | Needs the committed update's backup pair (kept until the next update) and the app to exit. Copies the CURRENT database to `updates/rolled-back-data/susu-<version>.db` (what was saved in the failed or abandoned version is kept, not merged), then restores the old binaries and database together through the same journaled `RollBack` (any cut-off is finished by `Recover`). Outcomes: rolled-back, aborted (app did not exit, nothing changed), no-backup, failed (`rollback-incomplete`; with a damaged backup the installed version is left as it is). With the failure reason the version is written to `failed-versions.json` before the restore starts. |
| Loop guard | `FirstStartGuard.IsFailed`, `AppUpdateService` | A version recorded as failed is not offered (check reports `version-failed-before`), not downloaded and not installed again; a newer version number is. A user's own rollback does not block the version. After a fallback the old version starts normally (a state for another version is removed). When the helper cannot roll back (no pair) the guard is cleared and the version on disk starts as it is: no lock-out and no endless relaunch. |
| User rollback | `AppUpdateService.CanRollBack` and `RollBack`, `ProcessUpdateLauncher.LaunchRollback` | Engine, service and helper are in place and tested, and name interrupted tasks like an install does. **No Settings button or `Update.Rollback` command is wired yet** (contracts, i18n, vitest outstanding); the error keys are already in zh and en. |
| DATA03 | `Database.Open`, `DatabaseVersionException` | An older build refuses a newer schema with a bilingual message and changes nothing; the fallback restores the paired database copy taken before the update (test with the real `Database` and a real migration). |
| Uninstall | `InstallerSupport.Uninstall`, `InstallerMode` | Data stays unless `--delete-user-data` (explicit choice, default No also when silent). `--data-root` must be a plain absolute path (else exit 2). Only a folder named `Su-Su` is ever deleted (`foldersRefused`, exit 12 otherwise); deletion walks the tree itself and unlinks junctions and directory symlinks without following them; read-only files go. Container profiles, login entry and kept screenshots as in F18.1. |

### Decisions

- **Anti-rollback marks stay unsigned.** Threat model: the marks, the journal, the staged files and the install folder are all in the current user's own profile. Someone who can write there can already replace the installed exe, so a MAC (DPAPI-bound or not) would not stop them. The checks protect against a wrong or hostile network response and against local mistakes, not against same-user code execution. Not signed; not changed.
- **A fallback does not merge data.** The database written by the abandoned version is kept next to the update state; the restored database is the one that matches the old binaries. Merging across schema versions was not attempted.
- **First-start confirmation is time-based** (15 s of running with the message loop up), because the app has no single "UI ready" signal; a crash later than that is not counted.
- Only a first-start failure marks a version as failed; a migration or health failure before the commit is user-visible and the user may retry (a transient failure should not block a release).

### Open

- No Settings button or command for the user rollback; the update URL is still read from `updates/update-source.json`, not from the settings schema, and the HTTP client does not use the proxy policy of Susu.Net (both left: they touch the settings contract and the network layer).
- `Program.FirstStartGate` and the 15 s confirmation are exercised through the guard class and the real helper, not through a real GUI start of two failing builds (that needs a deliberately broken second build).
- A real update of a running installed app, a real power cut, the compiled installer and a clean Windows 11 user install are still not run.
- The rolled-back data copy is not listed or restorable from the UI; it is a file in `updates/rolled-back-data`.
- `--install-dir` cannot be bound to a registered install location (none is registered); the binding is to the journal made by the app that staged the package.
