Decisions and behaviour:
- **File**. Plain: a zip of `manifest.json` (format 1, schema, app version, created, per-file SHA-256), `settings.yaml`, `plugins.json` (user package identities: id, version, signer, hash; no code). Encrypted: the magic `SUSUBAK` plus version byte 1, a length-prefixed JSON header (PBKDF2-SHA256, iterations, 16-byte salt, 12-byte nonce) and AES-256-GCM over the same zip with `secrets.json` added when keys are included; the header is the associated data. PBKDF2 uses 600,000 iterations on export. A plain file has an integrity check but no authenticity (anyone can rebuild it with a consistent manifest); that is why it carries no keys.
- **Keys**. Not exported by default. Including keys requires a password (8 to 256 characters) and the whole file is encrypted. A plain file with a `secrets.json` is refused on import (`secrets-unencrypted`). Imported keys are re-protected with the importing user's protector at preview time; the stage on disk holds a ready `secrets.dat` and never plaintext keys.
- **Authorization is never imported**. Grants are dropped on export and again on import, so every account must be re-authorized in the service settings; keys the backup did not bring show as not saved. A crafted settings.yaml carrying a grant for another origin ends with none (tested).
- **What a backup holds**: the settings (language, hotkeys, network, accounts without grants, instances, services, prompts, speech/OCR choices) and optionally keys. ARCHITECTURE 8.1 excludes the favorites database, so the backup holds no history, favorites, entries, outbox, logs or caches; the preview says how many favorites and open outbox rows stay untouched. The task text listed "history, favorites/entries/outbox" among things a restore would replace; the architecture and DATA09 say the DB is not imported, and this follows them (open item 1).
- **Bounds** (checked before the KDF or any entry is read): file at most 16 MiB; password at most 256 characters; KDF iterations 600,000 to 2,000,000 (outside it: `kdf-params`, no key derivation runs; a test times the refusal under 1.5 s); salt 16 to 64 bytes, nonce 12; entry count from the zip end record at most 16; only the four fixed names (anything else, including `plugins/...`, `susu.db`, caches and logs: `unexpected-entry`; separators, `..`, drive, stream or control characters: `path-escape`; duplicates refused); entry at most 8 MiB, total at most 32 MiB, expansion at most 100 times once an entry passes 1 MiB (counted while reading, so a lying header cannot get past).
- **Preview** (`Backup.Pick`, then `Backup.Unlock` for an encrypted file): verifies the whole file and writes only under `%LOCALAPPDATA%\Su-Su\import\staged`; the live `settings.yaml` and `secrets.dat` are untouched (hash-checked in tests). It reports per area current to backup counts (settings, accounts, instances, enabled services, prompts), the plugin list against what is installed (missing, built in, same, older, newer), the instances whose package is missing and will be disabled, accounts needing authorization with the keys the backup did not bring, local keys the restore removes, whether the schema is older (migrated), and the kept favorites and outbox counts. Conflict keys: `plugins-missing`, `services-disabled`, `accounts-need-authorization`, `keys-missing`, `keys-removed`.
- **Missing plugins** are disabled, not installed: every service of an instance whose package this install lacks is written `enabled: false`; the plugin list is information only and nothing is downloaded or unpacked.
- **Switch at the next start**: `Backup.Apply` (token only) marks the stage Ready. At start, after the journal recovery, `ApplyPending` verifies the staged hashes and re-parses the settings, fixes the final bytes (revision moved past the current file's) and records their hash, keeps a restore point (the old `settings.yaml` and `secrets.dat`, which stay DPAPI ciphertext) once per import, then commits both files through the existing journaled `ConfigTransaction`. A Previewed stage that was never confirmed is dropped. Any failure (tamper, invalid settings, disk full) clears the stage, leaves the old pair and records a Failed result the page shows until dismissed. An import that crashes the start three times is abandoned (`too-many-attempts`).
- **Undo**: the restore point is kept after a commit; `Backup.Undo` stages it as a Ready import of source `undo`, switched at the next start through the same path (and then its own restore point holds the config from before the undo).
- **Page**: export (keys checkbox, password, dialog), restore (dialog, password step, preview, apply, cancel), the scheduled notice, the last import result with dismiss, undo. The page never receives a path (file name only), a key or a grant. Passwords are cleared after use and when the window hides, and do not appear in any view.

Open items:
1. The backup does not hold favorites, entries, outbox or history (ARCHITECTURE 8.1). If a full data export is wanted, it is a separate feature on the F15 export path, not this one.
2. Speech, OCR and prompt-scope choices that name a disabled or missing service are restored as written; the existing availability rules treat them as unavailable, but the page does not list them in the preview.
3. The staging folder has the default folder ACL (the journal directory has no special ACL in F02 either); ARCHITECTURE says the transactions directory should match secrets. Not tightened here.
4. A restore always replaces `secrets.dat` (keys not in the backup are removed; the preview says how many). The pre-import pair is kept for one generation only: a second import replaces the restore point.
5. Dragging a `.susubak` onto the window is not wired (same as plugin drop); the page uses the dialog.
6. F17.2 (about, diagnostics, sensitive-value filter) and F17.3 (recovery drills with user notes) remain; the recovery-drill facts for wrong password, power loss and version mismatch already have tests here.
