## F16.1 scope and what is not covered

Commits: 12144cb (installer core), 4a32229 (host layer, contracts, picker, component), then the page wiring commit and the tests commit.

- Settings has a Plugins page (nav item, `PluginSettings.vue`, zh/en strings, dev-preview fixture). Commands `Plugin.Pick`, `Plugin.Confirm`, `Plugin.Discard`, `Plugin.Uninstall` are Settings-window only. The page never sends a path: the host opens the dialog, stages the package behind a token, and only the token returns to confirm.
- Permission diff (first install: everything requested; update: against the installed version; override: against the built-in) is shown before activation; a widening is flagged. Third-party signatures are shown as an accepted identity, not endorsement. Uninstalling an override restores the shipped version and the page says so.
- **Not done:** native drag-and-drop onto the Settings window is not wired (needs the WebView host's drag-drop hook). `ShellCoordinator.PreviewPluginPackageAsync(path)` is the entry for it and is tested. The Win32 open dialog (`Win32PluginPackagePicker`) compiles and was not run (no interactive desktop).
- **Host keyring is empty** in `Program.cs` until F18 embeds the offline root, so no package counts as host-signed in the product yet and a built-in id cannot be overridden there. The override path is tested with a test keyring.
- The three gaps this section used to list (sandbox read scope of the roaming folder, the running host not loading installed plugins, in-flight calls on install/uninstall) are closed by F16.2 below. The signer-change and signature-removed rules changed in F16.2: they are no longer refusals but held changes (UPD03).

## F16.2 scope and what is not covered

Commits: 48a64a6 (storage, installer, host controller, contracts), 6b0ae07 (composition root, tests), then the page, locale, docs commit. Full suite 1788 total (1786 pass, 2 skipped; one existing test that hard-coded schema version 4 was fixed to follow `Database.SchemaVersion`), vitest 209, vue-tsc clean, `ContractsGen --check` clean.

- **Held changes (UPD03).** `PluginPreviewInfo.ConfirmReasons` carries `signer-changed`, `signature-removed` and `permissions-expanded` (hosts, credential use or capabilities added against the installed version or the built-in it overrides; reductions apply without a hold). `Install(token, acknowledged)` refuses such a package with `install.needsConfirmation` unless the user ticked the box; it stays staged and the installed version keeps running. The Settings command `Plugin.Confirm` takes `acknowledged`. A package for a built-in id still needs the host signature and a higher version (F16.1).
- **Compatibility.** The manifest `apiVersion` outside `ProtocolVersions.SupportedPluginApi` is refused as `api-unsupported`, a `minHost` above the host level as `host-too-old`; both on a pick and on a staged update, with the page showing a translated reason, and the old version untouched.
- **Update staging.** `StageUpdate(path)` runs the same validation as a pick, requires an installed package, and keeps the package aside (one per package id, a newer one replaces an older one, a manual pick does not discard staged updates, a restart clears staging). `Install(token)` re-hashes the staged bytes and refuses `install.changed` if they changed, and `install.stale` if the installed version differs from the one it was judged against. A package that fails validation is deleted at once and nothing changes.
- **Update source (open, by design).** DEV-PLAN and PLAN define neither the update manifest schema nor an endpoint (PLAN 4.6 names an optional manifest `update:` URL and requires a signed update manifest verified before parsing). Nothing was invented: `IPluginUpdateSource` is the port (check, then fetch a package file), `PluginUpdateService` is the serial check that stages what a source offers and reports a source error as a failure, never as up to date. The product registers no source, so the Plugins page shows the check button disabled with an explanation. The 24 h / 15 s background schedule shared with the app updater (ARCHITECTURE 10) is not built; it belongs with the F18 updater. The manifest `update` field is not parsed and "update origin" is not part of the permission diff yet.
- **KV namespace (DATA04).** `plugin_kv` is keyed by package id (schema 4, migration keeps existing rows with the active version winning a clash). `Broker.PluginKv` backs `$store` with it; the id comes from the call's grant, never from the plugin, so there is no path to another package's data. Updates keep the data; uninstall keeps it unless the user ticks "also delete this plugin's data" (`PluginUninstallRequest.RemoveData`). A built-in override shares the built-in id's data. Quotas are unchanged (1 MiB per package, 32 MiB total). Without a `PluginKv` the broker still uses its in-memory store (tests, tools).
- **Host restart and in-flight calls.** `PluginHostController` detaches the live session from the supervisor (`Supervisor.Recycle`, not counted as a crash), cancels the changed package's in-flight calls in it (`HostSession.Interrupt`: upstream I/O aborted, the child fails each call as `cancelled`, nothing replayed), lets other packages' calls finish, and disposes the old session after it drains or after 30 s. The next call launches a fresh session that loads the wired packages (a host-signed override's active directory replaces the shipped one) plus every installed package. The installer calls it after a committed install or uninstall (never after a rollback) and reports the cancelled count; the page names the in-flight calls before the action and counts them after. A host that cannot restart does not undo a committed switch. `ActiveDirectory` waits for a switch in progress so a launch never loads a version still being checked.
- **Sandbox read scope and load probe.** `HostSession.Options.ExtraReadRoots` grants one session's AppContainer read/execute on the packages folder only (managed ACL entry per container SID, serialized, removed when the session ends) and passes the root to the child, whose `plugin directory outside host resources` check now accepts it (path-prefix safe). Staging is never granted. `PluginLoadProbe` is the post-switch health check in the product: a throwaway sandboxed host loads the activated package from its real folder; a package that parses but cannot load rolls back (`install.healthFailed`). The probe loads; it does not invoke a capability.
- **Not done or open.**
  - No update source or schedule (above). The host keyring is still empty until F18, so host-signed overrides cannot happen in the product.
  - Installed user packages are loaded into the plugin host, but the translation, OCR, speech and vocabulary pipelines still wire only the shipped catalogs: nothing creates a service instance from a third-party package, so an installed third-party package is present in the host and invocable by id but not selectable as a provider. A host-signed override of a wired package is used by the live pipeline (its directory replaces the shipped one at the next launch).
  - A package's `limits.memory`, per-capability timeouts and `update` manifest fields are not parsed; load uses the 64 MiB default.
  - KV retained after an uninstall is reachable by any later package that reuses the id (there is no per-signer ownership of the data). Stale ACL entries for a deleted container profile could remain after a hard crash; they are inert.
  - Native drag-and-drop and the interactive file dialog remain unverified on a real desktop (F16.1); the new page controls were verified with vitest and the fake bridge, not in a running window.
  - Foreign-PID, other-user and remote-pipe X05 variants were not re-tested (F04 owns them).

## F16.3 scope and what is not covered

Commits: e472b34 (CLI, loopback replay, cases for the shipped plugins), then the tests, guide and records commit. Author guide: [PLUGIN-AUTHOR-GUIDE](../../development/PLUGIN-AUTHOR-GUIDE.md).

- **Commands** (`tools/Susu.PluginCli`, NativeAOT `susu-plugin.exe`; exit 0 ok, 1 package or case failed, 2 usage or unreadable input): `init` (one template per capability: translate, dictionary, detect, ocr, tts, asr, vocab; refuses a non-empty folder or an invalid id), `check` (existing manifest and file checks, plus: entry file exists and has `export default`, a warning for a declared capability with no method, the cases file parses and uses declared capabilities, and the signature is now verified for real through `PackageTrust.Verify`; the F04 code looked for `manifest.sig`, while the installer reads `signature`), `test`, and two additions the guide needs: `pack` (zip without author-only files, optional Ed25519 signature the installer verifies) and `keygen`.
- **`test` replays cases through the real sandbox.** The CLI stages `susu.exe` plus the package (author files excluded), starts `HostSession` (AppContainer, QuickJS, IPC, `Broker`/`NetworkBroker`), and per case runs a loopback TCP vendor with the canned answers (`susu-plugin.test.json`: request, vendor replies, test secrets, input files as real file leases, expected result subset or error class, expected vendor requests). Only the loopback origin is granted, so nothing reaches a real vendor. Malformed cases files exit 2 with the JSON path. A timed-out case restarts the host for the next one. The old single-call form (`--capability`, `--request`, real manifest hosts) is kept and still used by `PluginCliIntegrationTests`.
- **Convention the replay relies on:** the plugin reads its vendor address from `ctx.config.baseUrl` (every shipped package already does; the templates do). A plugin with a hard-coded URL cannot be replayed (the call is refused by the origin policy and the case fails with a clear class).
- **Shipped packages:** 14 cases files in `tests/plugin-cases/<package>.test.json` (2 to 5 cases each: a success, and the vendor failures that package maps). They are contract-level cases written from the packages' own code and the existing plugin tests; vendor answer shapes are canned, not recorded from live vendors (no accounts here). `Every_shipped_plugin_has_a_cases_file` fails when a package is added without one.
- **Tests (`PluginAuthorCliTests`, 39):** every template through init, check and test (7); init refusals; every shipped plugin check plus recorded cases (14); cases-file presence; 9 malformed-file variants; wrong expectations (result, error class, request count, request body); vendor timeout and a following case still passing; a plugin that throws, exhausts memory or stack, or loops forever (contained: classified `bad_response` or `timeout`, the next case runs); undeclared capability and `--filter`; missing cases file or host; missing entry file; pack contents, keygen refusal to overwrite, signed package verifies in `check`, a tampered file fails it. The tests skip visibly (`Assert.Skip`) when either executable is not published.
- **Not done or open.**
  - A real plugin-host process crash (the `unavailable` class) is not forced by any test: a JavaScript hang, out-of-memory and stack overflow are all contained by the engine and reported as errors, and no plugin code found here kills the child. The mapping exists (a closed IPC channel while a call is open becomes `unavailable`) and is untested.
  - `test` does not exercise the host's own pipelines (retry, result validation such as ASR segment ranges or OCR box limits, SSRF/DNS rules for cloud origins, which a loopback replay cannot show) or per-instance account authorization (it uses the single-package secret store of the broker's pre-F07 fallback).
  - `ctx.$store`, `$ws` and `ctx.$http` redirects are available to a plugin under test but the cases format has no way to assert on stored data or to script a redirect chain beyond the ordered vendor replies.
  - PLAN 4.11 describes the CLI as a Node script with a CLI-side IPC; what exists is the .NET tool using the product's own `HostSession`. PLAN 4.11 was not edited.
  - The sandbox `crypto` and `URLSearchParams` gap left open by F16.3 is closed by F16.4 below.
  - TEST-PLAN has no case that names `susu-plugin` or the CLI; the exit criterion "all existing plugin CLI contracts pass" is covered by the 14 shipped packages plus the 13 older integration tests.

## F16.4: sandbox `crypto` and `URLSearchParams` (carried from F09.1)

Exactly the surface PLAN 4.3 lists, added to the QuickJS bridge (`native/quickjs-bridge`): `crypto.getRandomValues`, `crypto.randomUUID`, `crypto.subtle.digest` and `URLSearchParams`. Full suite 1861 total, 1859 pass, 2 skipped (no microphone, no MP3 encoder).

- **Where.** `webapis.js` is the source; `tools/gen-webapis.mjs` turns it into `webapis.inc` (a C string literal, checked in), included by `bridge.c` and evaluated once per runtime before the lockdown. Two C natives back it: `random(n)` (`BCryptGenRandom`, system RNG, 0..65536 bytes) and `digest(id, buffer)` (CNG `BCryptHash` for SHA-1/256/384/512). The plugin gets neither handle nor key material: the natives only return random bytes or a hash of bytes the plugin passed in. `susu_quickjs.dll` was rebuilt (`cmake --build artifacts/native --config Release --target susu_quickjs`; `tools/build-native.ps1` also does it) and `susu.exe` republished (`dotnet publish src/Susu.Host -c Release -r win-x64`).
- **Behaviour.** `getRandomValues` accepts integer typed arrays only (`TypeMismatchError` for floats, DataView, plain arrays) and at most 65536 bytes (`QuotaExceededError`), and fills only the view's window. `randomUUID` is a v4 UUID. `subtle.digest` takes a name or `{name}` (case-insensitive), an ArrayBuffer or view (only the view's bytes), and resolves an ArrayBuffer; other algorithms reject `NotSupportedError`. `crypto` and `crypto.subtle` are frozen and the global is not writable. `URLSearchParams` follows the URL Standard form-urlencoded rules (`+` is a space on parse, space is `+` on serialize, malformed `%` kept literally, invalid UTF-8 and lone surrogates become U+FFFD, stable sort by UTF-16 code units, live iterators, `size`, two-argument `delete`/`has`).
- **Tests.** `SandboxWebApiTests` (33): SHA-1/256/384/512 vectors, empty input, a 56-byte NIST vector, views with offsets, randomness limits and surface; `URLSearchParams` edge cases (empty, duplicates, unicode, `%` malformed, `+` against `%20`, sort, iteration while appending, bad constructor input). It runs the real QuickJS bridge in-process (the test project now copies `susu_quickjs.dll`). `PluginAuthorCliTests` gained one case that runs a plugin using all four through `susu-plugin test` in the real AppContainer sandbox (40 in that class).
- **Not done.** `URL` itself is not in the bridge (PLAN 4.3 lists `URL / URLSearchParams`; this item was scoped to `URLSearchParams`), and neither are `TextEncoder`/`TextDecoder`, `setTimeout`/`queueMicrotask`, `AbortController` global, `structuredClone`, `console`: the same list in PLAN 4.3 promises them, so a plugin author still cannot rely on them. `susu-plugin.d.ts` does not declare the new globals (it is generated from `PluginApi.cs`). `subtle.digest` hashes in one call (bounded by the 4 MiB message limits); no streaming. Plain SHA digest only: no HMAC, per PLAN 4.3.

### Defects found and fixed

| Id | Severity | Defect | Fix |
| --- | --- | --- | --- |
| V1 | High | `check` on a manifest nested ~20000 deep overflowed the stack (process crash, exit 0xC00000FD). | `PackageManifest` reader refuses nesting deeper than 32 (`Manifest.cs`). |
| V2 | High | A tampered `journal.json` naming `..` / a path in `PackageId` or `Version` made start-up recovery delete outside the packages folder. | `PluginInstaller.Recover` ignores a journal whose id or version is not a plain name (`IsPlainName`). |
| V3 | High | A junction inside a package folder was followed: `check` passed and `pack` put a file from outside into the package. | `SafePackage.Validate` walks folders itself and reports a `reparse-point` issue instead of descending into a link. |
| V4 | Medium | `pack` produced a package the installer refuses (`aux.txt.bak`: reserved device name with an extension). | `SafePackage` device-name rule now uses the stem before the first dot, like `SafeUnzip`. |
| V5 | Medium | A cases file with duplicate keys crashed the CLI with an unhandled exception. | `CaseFile.Parse` turns the duplicate-key error into a `CaseFileException` (usage error). |
| V6 | Medium | A plugin-host child that crashed was never disposed by the supervisor: its container profile and read grants on the packages folder stayed on disk. | `Supervisor.OnDisconnected` disposes the crashed session on a worker thread. `SupervisorTests.A_crash_never_resends_calls_a_new_session_never_saw` asserted the old behaviour (`Disposed` false); corrected to expect disposal (bad expectation, same root cause). |
